# 事故口味的查询

这不是独立的来源类别，是**叠加**在某个源上的检索口味。目标代码看起来像防御性代码时，把它接到
那个调查者的 prompt 后面，让它在自己那个源里跑事故口味的查询。

判据：目标里有 null 检查、重试逻辑、超时处理、限流、feature flag、出口限制、OOM 处理。

## 按源的口味

- **源码史**：message 里带 `fix for incident`、`add defensive check`、`revert` 之后紧跟
  `re-apply with...` 的 commit，是很强的信号。查目标改动前后紧邻的 revert / rollback。
- **工单**：找标签带 `incident`、`sev-*`、`postmortem-action-item`、`reliability` 的。
- **本地笔记 / 长文档**：找复盘、事后分析、runbook。复盘里写「加了 X 来防住 Y」就是近乎直接的
  证据。
- **可观测**：找目标改动日期附近的告警与变更事件。事故期间的一次配置回滚，常是防御性代码的直接
  动因。
- **错误跟踪**：找目标防的那种错误，看它的首次出现与频率轨迹。
- **群聊**：本机没有这个源，跳过并记 `not available in this environment`。

## 规则

- 事故记录常带明确时间线。**时间线就是证据**：把它与目标改动日期并排放，让先后关系自己说话。
- 复盘文档里的行动项（action item）常直接对应代码里的某一段。找到那条行动项就是找到了动机。
- **事故之后不一定有防御性代码，防御性代码也不一定来自事故。** 找不到就记缺口，不要硬套。
