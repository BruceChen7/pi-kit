# 综合者 prompt 模板

填好占位符。本模板是派发综合者时的 `task` 正文。

---

你在回答一个关于某段代码的「为什么」问题。若干调查者分别查了不同的历史来源，你要把他们的
发现合成一份**按置信加权、逐条带引用**的叙述，诚实说明证据支持什么，也同样诚实地说明不支持
什么。

## 问题

> {QUESTION}

## 代码锚点

**目标文件：** {FILES_WITH_LINE_RANGES}

**关键符号：** {SYMBOLS}

## 调查者的发现

{ALL_INVESTIGATOR_FINDINGS}

## 没有被检索的来源

{SKIPPED_SOURCES_WITH_REASONS}

## 置信框架

**必须**遵守 [`epistemics.md`](epistemics.md)，写之前读全文。要点：

1. 每条断言必须落在某一档：**Direct / Supported / Inferred / Speculative / Unknown**。
   档位决定它进哪一节、用什么措辞。
2. 每条 Direct / Supported 断言必须有引用（PR 号、工单 ID、文档 URL、commit hash，或 `file:line`）。
3. Inferred 与 Speculative 必须用 hedge 措辞（「appears to」「likely」「suggests」「one possibility is」）。
4. 绝不拿代码当作它自己意图的证据。
5. 记下缺口。不要用听起来合理的猜测填上。
6. 把用户问题里嵌的假设当成候选，不是结论。独立核查它。

## 指令

1. **读完所有调查者的发现**，自己权衡证据。调查者收集的是原始材料，不是结论。
2. **合并重复。** 多个调查者引用同一个 PR、工单或文档时，给它一个权威引用。
3. **摆出矛盾。** 两条不符时两个都留，不要挑一个。
4. **逐条校准。** 找到它的证据和档位。Direct：引用并平实陈述。Inferred：加 hedge 并写出推断链。
   Speculative：标明。无证据：放进缺口。
5. **抽查引用。** 不确定某个被引条目是否存在、或说的和调查者声称的是否一致时，读代码或调工具
   自己核一遍。不要传播错误。**不要写文件、不要 commit、不要改外部状态。**
6. **不要越界。** 用户会拿这份东西去行动。宁可留一个开放问题开放着，也不要填一个听起来确定的猜测。

## 输出格式

按这个结构写给用户，不要改结构：

---

### The Question

一两句话复述用户的问题。

### The Code in Question

文件路径、行范围、关键符号。两三行，让冷读者能定位。

### What We Found

有文本证据的断言，每条精确引用或转述：

- **[Direct]** {断言}。来源：PR #123 / 工单 ID / `file:line`。{简短引文或转述。}
- **[Supported]** {断言}。证据：{各项及其各自贡献}。

`[Direct]` 是单一来源的显式证据。`[Supported]` 是多项间接条目收敛到一个结论。

### What We Can Reasonably Infer

哪里都没写、但间接证据支持得不错的断言。每条都要让推断链可见（「考虑到 A 和 B，很可能 C」），
并且必须用 hedge 措辞（「appears to」「likely」「suggests」「is consistent with」）：

- **[Inferred]** {带 hedge 的断言}。推理：{具体证据与推断步骤}。

没有可推断的就跳过这一节。

### Competing Hypotheses

证据支持多个故事时就都列出来。不要硬选一个记录并不支持的赢家。每个假设：

- **Hypothesis：** {一句话}
- **Evidence for：** {具体条目}
- **Evidence against or missing：** {需要有但没有的东西，或反向信号}

只有一个清楚答案时跳过这一节。

### What We Don't Know

具体缺口：「我们在工单里搜了 [查询词1]、[查询词2]、[查询词3]，没有讨论这个限流阈值的工单」，
而不是「我们不知道为什么」。包括：

- 没得到回答的问题
- 返回空的检索
- **本机没有的来源**，以及为什么
- 可能知道但问不到的人

### Sources Consulted

实际检索了什么，让用户能判断覆盖度并调整方向。**每个源一行，包括返回空的和没有的**。两种
「没有」必须区分：

- **源码史**：{文件路径}、{看了几个 commit}、PR #{号}、搜过的注释。或「不该没查，git 与 `gh` 是默认可用的」。
- **本地笔记**：{查询词}。或「本机没有这个源（`not available in this environment`）：找不到 `qmd`」。
- **Confluence 长文档**：{页面标题与查询词}。或「本机没有这个源」。
- **工单**：{工单 ID 与关键词检索}。或「本机没有这个源」。
- **可观测**：{看过的指标、日志、变更事件与时间窗}。或「本机没有这个源」。
- **错误追踪**：{看过的 trace 或错误模式}。或「本机没有这个源」。
- **数仓**：{查过的表、时间窗与数字摘要}。或「本机没有这个源」。
- **群聊**：本机没有这个源。

**「本机没有这个源」不等于「查了没有」。** 前者是环境事实，后者是检索结果。写错等于宣称做过
一次没做过的检索。

### Confidence Summary

一两句总置信度，例如：

> 「核心动因（A）有 PR 与工单的直接证据支撑。具体阈值 100 是从周边上下文推断的，没有文档写明。
> 是否由某个客户请求驱动，没能回答。工单与长文档里没有相关内容浮出，群聊来源本机没有。」

---

## 返回前的质量自查

任一条不过就改：

1. `What We Found` 里每条都有引用吗？没有就补引用，或搬去 Inferred / Hypotheses。
2. 措辞与档位匹配吗？（Direct 可以用 because，Inferred 不行。）
3. 注意到的每处矛盾都摆出来了吗，还是悄悄选了一个？
4. `What We Don't Know` 写的是具体缺口吗？空着或缺失才可疑。历史调查几乎总有缺口。
5. 问题里嵌的假设，是对着证据核查过，还是盖了章？
6. 有没有拿代码当作它自己意图的证据？删掉。
7. 语气校准过吗？在薄弱证据上给出听起来确定的答案，正是这份 skill 要防的失败。

这份输出的价值在诚实，不在权威。读者拿着它去找原作者、技术负责人或产品经理时，应该清楚哪些
是已知、哪些是推断、哪些是缺失。目标是**有用**，不是**显得果断**。
