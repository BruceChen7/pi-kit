# 错误跟踪

本机没有这个源时（`~/.agents/skills/` 下没有 `trace-analysis` / `log-analysis`，或凭据没配）：
**不要报「查无此项」**，在 `Sources Consulted` 里写成 `not available in this environment`，
并说清缺什么。

## 这个源里有什么

线上真实抛出的异常，以及它们的演变。这是「这段防御性代码当初在防什么」最直接的证据源。

- 错误事件：异常类型、消息、栈、发生次数
- 首次出现 / 最后出现的时间
- 影响的版本（哪个版本开始出现、哪个版本修掉）
- 标签分布：环境、用户、版本
- 面包屑：出错前发生了什么
- 关联的 trace

## 怎么搜

**按探测结果选工具。** 本机可能有 `trace-analysis`（按 trace ID 拉链路）与 `log-analysis`（PQL
查日志）。都在 `~/.agents/skills/` 下且带 `fetch-*.sh`，**子会话有 `bash`，可以自己跑**。调用方式
读各自的 `SKILL.md` 与 `assets/`，不要凭名字猜参数。

检索词从目标代码里取：

- 它捕获的异常类名
- 它的函数名 / 类名 / 文件路径
- 它检查的那些错误消息字符串
- 它防御的那种错误模式

拿到候选后，重点看四个量：

1. **首次出现 / 最后出现**：停止时间点对不对得上目标的落地日期？
2. **影响版本**：哪个版本见过它，哪个版本修掉了它？
3. **频率轨迹**：是尖峰后消失，还是一直在？
4. **栈与面包屑**：栈是否经过目标代码？标签与面包屑是否匹配它防的那种条件？

## 好证据长什么样

- 某个错误类别的次数在一个防御性改动合入后几天内掉到接近零
- 一条错误的首次出现时间早于目标代码，且栈正好落在它守护的那个位置上
- 目标代码的注释或 message 里出现的字符串，与线上错误消息逐字一致
- 一次错误尖峰紧邻目标改动之前

## 常见坑

- **相关不等于因果。** 一个错误类别变少可能有别的原因（流量变了、另一个修复上线了、采样变了）。
  查邻近改动。
- **采样与留存。** 错误数据常被采样，且留存期有限。找不到相关窗口是**缺口**，不是空结果。
- **只看聚合。** 汇总数字会盖掉具体的栈。至少读一条完整事件的上下文。
- **AI 生成的根因分析不是证据。** 有这类工具时把它当假设生成器，等级记 Inferred，不要当权威。
  真正的一手证据是事件与栈本身。
- **凭据没配。** 脚本报鉴权失败就停下记缺口。

## 要返回什么

每个相关条目：

- 错误 ID 与标题
- 首次 / 最后出现的时间戳
- 事件数（知道采样率就写）
- 影响的版本
- 一段有代表性的栈或上下文片段，说明与目标的关系（逐字摘录，不要概括）
- 与目标落地日期的先后关系
- 相关评论或处理说明
