# 置信与措辞

证据是历史的、碎片化的，有时互相矛盾。这份文档讲两件事：怎么给它分档，以及怎么把档位写进措辞。代码说明它做什么，不说明它**为什么存在**。动机活在 commit、PR、工单、文档和对话里，它们都不完整、有偏向，有时根本不存在。假装不是这样，就会产出听起来很确定的猜测。

一档一句话：**每个结论必须落在某一档里，档位决定它写在哪一节、用什么措辞。**

## 五档

### 1. Direct（直接）

有显式文本引用回答问题：作者**写下过**为什么，而不是「代码这么做，所以他大概是想……」。

例：PR 描述写「修掉 >1000 条时无法翻页的 bug」；工单写「加这个是因为 Acme 在安全评审里提的」；注释写 `// 限制在 100，上游 API 会拒掉更大的值`；设计文档写「选 A 不选 B，因为要跨重启保留」；作者在群里说「换成这个做法，旧的在测试里很飘」。

措辞：确定、现在时、带引用。「之所以是这样，是因为 X。」

### 2. Supported（多项收敛）

多项间接证据指向同一结论。没有单一来源明说，但来源之间的模式让它很可能成立。

例：PR 标题写「提升性能」，工单打了 `perf` 标签，同期相关 commit 都在同一条热路径上；或者随改动加的测试全都在测超大输入；或者作者同一周的其他 PR 都提到同一次事故。

措辞：确定但明确说明是推出来的，逐项引用。「证据强烈指向 X：[具体各项]。」

### 3. Inferred（推断）

对上下文的一个合理解读，没有任何东西显式支持它。这是**你的解释**，不是记录里的事实。

例：PR 没说为什么，但错误在线上发生（从事故频道的时间点看），修得也急（当天就合），所以很可能是一次热修；或者函数名像是重试逻辑，重试次数 3 也对上了代码库里别处的三重重试惯例。

措辞：带 hedge，且把推断链写出来。「考虑到 A 和 B，C 看起来很可能，因为 D。」

### 4. Speculative（猜测）

在薄弱证据上的一个可能说法，别的解释同样成立。值得摆出来，因为用户可能知道哪个对，但要标明这是猜。

例：「这可能是当年绕过某个浏览器 bug 的写法，不过我们没找到当时的证据」；「这个阈值有可能是为了对上某个 SLA 承诺，但没有文档提到它」。

措辞：「有一种可能是 X，但我们没有直接证据。」通常与别的可能一起放在 Competing Hypotheses 里。

### 5. Unknown（未知）

找过了，找不到。这是一个有效且重要的结果。要写下来。

措辞：「我们搜了 X、Y、Z，没有找到为什么。」

说清**搜了什么**。「我们没能查出来」远不如「我们在工单里搜了 A 和 B，扫了 2023 年以来碰过这个文件的 6 个 PR，还在仓库里 grep 了匹配该阈值的字面量，都没有浮出动机」有用。

## 措辞表

**置信词**意味着 Direct 或 Supported，必须紧挨着引用。**永远不要**把它们用在推断上：

> because、the reason is、was designed to（主张作者意图）、fixes / addresses / solves（主张改动达成了目标）、the team decided（主张发生过一次群体决策）

**hedge 词**表示这是解读，不是汇报。「What We Can Reasonably Infer」一节里要大量使用：

> appears to、seems to、likely、suggests、is consistent with、one reading is、plausibly、may have been、the evidence points toward

**避免的词**：

- 「obviously」。真明显的话用户就不会问了。
- 「clearly」。它几乎总是出现在一个并不清楚的论断前面。
- 「of course」。同上。
- 「just」（比如「只是为了性能用的 X」）。这是打发，通常正好盖住了不确定。
- 「I think」/「I believe」。你在综合证据，不是在发表个人意见。用「the evidence suggests」。

## 别做合理化

今天「说得通」的代码，可能是为了一些已经不适用的理由写的，或者当时就是错的。不要把一条干净的动机反装到混乱的历史上。不要假定作者做了「对的事」，再倒推为他辩护。不要假定一致的写法是有意为之，它可能是复制粘贴。也不要把没有证据当成不存在的证据。

## 谄媚陷阱

用户常在问题里塞一个假设：「我们为什么这么做，我猜是为了性能？」

不要顺着确认。那个猜测是检索的开端，不是待验证的结论。把它当成众多候选之一，独立核查证据。证据支持就带引用地说支持；不支持也直说，并给出证据**真正**支持的东西。

## 证据互相矛盾时

两个来源都列出来，带引用。不要挑那个更顺眼的。例如工单写「为了客户 X 的合规要求」，PR 写「清理这一块的技术债」——两者可能都对（工单是动机，PR 是作者自己的说法），也可能有一个是错的。让用户自己判断。

## 证据缺失时

一个诚实的「不知道」是这份工作最有价值的产出之一。用户由此知道答案不在显眼的地方，需要去问人（原作者、产品负责人、组长），或者可以决定这事不值得再追。

反过来，不标记缺口、用一句听起来确定的猜测填上去，会主动伤害用户，因为**他会照着那个猜测行动**。

每个缺口都要写具体：问题是什么、搜了哪些源、在每个源里搜了什么、找到了什么（没有，或者只有擦边的材料）。

## 交付前自查

综合者交付前逐条过：

1. `What We Found` 与 `What We Can Reasonably Infer` 里的每条断言，要么有引用，要么搬去 Inferred / Hypotheses。
2. 措辞与档位匹配（Direct 可以用 because，Inferred 不行）。
3. 注意到的每处矛盾都摆出来了，不是悄悄选了一个。
4. 有 `What We Don't Know` 一节，且写的是具体缺口。历史调查几乎总有缺口；这一节空着才可疑。
5. 问题里嵌的假设被独立核查过，不是盖了章。
6. 没有拿代码当作它自己意图的证据。
7. 语气校准过。在薄弱证据上给出听起来确定的答案，正是这份 skill 要防的失败。

这份输出的价值在诚实，不在权威。读者拿着它去找原作者、技术负责人或产品经理时，应该清楚哪些是已知、哪些是推断、哪些是缺失，从而能问出对的问题。目标是**有用**，不是**显得果断**。
