# How

探索代码库，回答「X 怎么工作」。产出的是一份**资深工程师上手一个子系统**所需的架构解释：
够建立可用心智模型，不至于读成带注释的源码流水账。

默认中文交付。`file:line`、符号名、命令原样保留。

## 一、评估复杂度

范围含糊就先说明你的理解，然后继续探索；用户会纠正。

- **简单**（单个模块、一个小工具、一个窄问题，比如「函数 X 怎么工作」）：**不派探查者**。
  派一个解释者，它自己边探边解释，模板用 [`references/explainer-prompt.md`](references/explainer-prompt.md)
  并去掉其中「探查者发现」那一节。直接到第四节。
- **复杂**（跨多文件或多服务的子系统、横切功能、整个架构概览）：走第二节。

**拿不准就走简单档。**

## 二、探查（仅复杂档）

把问题拆成 2 到 4 个**不同**的角度，每个是一个切片。同一条消息里一起发出
（`subagent`，`agent: "explore"`，`background: true`），一次 `subagent action: "wait"` 收。

- 每个探查者的 prompt 用 [`references/explorer-prompt.md`](references/explorer-prompt.md) 填好角度。
- **不要试图覆盖全部**：每个探查者在自己那个角度上深挖，各自返回。
- 子会话看不到本对话，`task` 必须自包含：问题、它的角度、输出格式。
- **原始材料留在子会话里**，主线程只收它们的结论（`guard-the-context-window`）。

## 三、综合（仅复杂档）

探查者都回来之后，派一个解释者（`subagent`，`agent: "explore"`）。给它
[`references/explainer-prompt.md`](references/explainer-prompt.md) 填好，附上所有探查者的发现。

解释者要：

- **合并重叠**：几个探查者查了同一处时，合成一段描述。
- **解决矛盾**：发现互相不符时，自己去看代码确认，不要摆着不管。
- **把切片拼成一张图**：让冷读者读完能建立完整心智模型。

## 四、呈现

把解释者的输出交给用户。可以为清楚起见轻度编辑、补一点对话上下文，**但不要大幅重写**。

输出分节（细节见 `references/explainer-prompt.md`，不适用的节可以省）：

1. **Overview** — 一两段：这是什么、做什么、为什么存在。读完这一节就能决定要不要继续读。
2. **Key Concepts** — 跟着后面的内容所必需的类型、服务或抽象，简短定义。
3. **How It Works** — 主体，最长的一节。走一遍流程：什么触发它、逐步发生什么、数据去哪、
   决策点在哪。用散文，不要伪代码。
4. **Where Things Live** — 文件/目录地图，只列要开始在这里干活所需的那几个。
5. **Gotchas** — 不显然的地方、令人意外的行为、历史包袱、坑。没有值得写的就省掉。

## 写法

- **用具体语言，不要用「关于抽象的抽象」。** 说「`UserService` 调了 `AuthClient.refresh()`」，
  不说「服务委托给客户端」。
- 引用具体文件与函数，让读者知道去哪看；除非某个片段对论点必要，不要贴大段代码。
- 流程涉及多个组件互相对话、或数据分阶段变换时，**画一张图**。用 mermaid（```` ```mermaid ````）画
  结构化流程（时序图、流程图、组件图）。画完先 `validate_mermaid` 校验，需要看图再 `render_mermaid`。
  **图是用来澄清的，不是装饰。** 散文已经讲清就跳过图。
- 复杂的地方要说清**为什么复杂**，不要只是描述这份复杂。简单的地方不要凑字数。
- 有贴切的类比就用，没有就不要硬造。
- 探查者标了未解问题或缺口时，**如实说出来**，不要藏起来。

## 边界

- **只解释，不改代码。**
- 不把「文件名对上」当成理解；说不清数据怎么流就是没懂。
- 不把探查者的原始输出整段贴回给用户。
- 查动机、历史、某个取值为什么是这个数，走 `/skill:why`，不要在这份 skill 里猜。
