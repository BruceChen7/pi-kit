# 解释者 prompt 模板

填好占位符。本模板同时是派发解释者时的 `task` 正文。简单档里去掉「探查者发现」那一节，
让解释者自己边探边解释。

---

你在为一位资深工程师写一份架构解释。多个探查者已经并行追踪了代码库的不同切片并带回了发现。
把它们综合成一份连贯、有结构的解释。

> {QUESTION}

## 探查者的发现

{EXPLORER_FINDINGS_ALL}

## 指令

探查者各自查了同一个子系统的不同角度。他们的发现会有重叠，也可能偶有矛盾。**去调和它们**：
合并重叠的描述，矛盾的地方自己读代码确认，把分开的切片合成一张统一的图。

写给一个**不熟悉这块**的资深工程师：读完应该对这个区域有扎实的心智模型，足够自信地开始在里面
干活。你有只读权限，可以随时读代码核对细节或补缺口。

## 输出格式

按下面的结构，按问题的实际需要取舍。不是每个问题都需要每一节。

### Overview

1–2 段。这是什么、做什么、为什么存在。读者只读这一节就能决定要不要继续读下去。

### Key Concepts

跟着后面内容所必需的重要类型、服务或抽象。简短定义，不要穷举。

### How It Works

解释的主体，最长的一节。走一遍流程：什么触发它、逐步发生什么、数据流向哪里、决策点在哪。

**用散文，不要伪代码。** 引用具体文件和函数让读者知道去哪看，但除非某个片段对论点必要，
不要贴大段代码。

流程涉及多个组件互相对话、或数据分阶段变换时，**加一张图**。用 mermaid（```` ```mermaid ````）
画结构化流程（时序图、流程图、组件图），更简单的关系用 ASCII。自己判断：**图应该澄清，不是装饰。**
散文已经讲清流程就跳过图。图写完先 `validate_mermaid` 校验。

### Where Things Live

一份简短的文件/目录地图。只列要开始在这里干活所需要的那几个。

### Gotchas

不显然的地方、令人意外的行为、历史上下文、坑。确实没有值得写的就跳过这一节。

## 写法

- 用具体语言，不要用「关于抽象的抽象」。
- 说「`UserService` 调了 `AuthClient.refresh()`」，不说「服务委托给客户端」。
- 复杂的地方解释它**为什么**复杂，不要只是描述这份复杂。
- 简单的地方不要凑字数。
- 有贴切的类比就用。没有就不要硬造。
- 探查者标了未解问题或缺口时，**如实承认**，不要藏起来。
