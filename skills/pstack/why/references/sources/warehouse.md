## 这个源里有什么

产品与分析这一层：用户**实际**做了什么、跑过哪些实验、功能使用怎么演变、某个阈值常量是哪来的。

它和可观测那一源互补。可观测是基础设施/运行时视角；这里是产品/数据视角。

- 产品行为事件：功能调用、点击、接受/拒绝、提交、客户端上报的错误
- 用量与计费事件：用于成本或容量驱动的决定
- 实验 / feature flag：曝露表与结果表。**schema 因公司而异**，先探再信表名
- 系统表：查询历史、计算资源、计费、审计
- 数据血缘：哪个下游依赖了这个表/字段
- 分析脚本与 notebook 的产物

## 怎么搜

**按探测结果选工具。** 本机可能有 `datastudio-hive-query`（Hive / Presto 只读 SQL），以及
提供 A/B 实验数据的 MCP。前者带可执行脚本，**子会话有 `bash` 可以自己跑**；MCP 只能父会话查，
父会话查完把结论当锚点发下去。

调用方式读各自的 `SKILL.md` 与 `references/`，不要凭名字猜。

**先定向，再查。** schema 因公司而异，先探再信表名：

```sql
SHOW TABLES IN <db>.<schema> LIKE '*<关键词>*';
DESCRIBE TABLE <db>.<schema>.<table>;
```

**每个查询都要带时间窗。** 这些表很大，无限定的扫描会超时。用时间戳列，
窗口按上线日期前后各约 30 天，有强理由才放宽。

**用加工过的模型，别用原始表。** 去重、定型、聚类的中间层比原始事件表好查。原始表只在还没有
加工层、或需要最新几小时的数据时用。

### 容易有收获的几个模式

1. **事件使用轨迹。** 相关模型在上线日期前后 ±30 天的日计数。合入后一两天内从零跳到稳定量，
   是很强的旁证：这次改动启动了该功能。衰减到零则提示下线或删除。
2. **阈值常量的来历。** 合入**前** 14 天里相关属性的分布（中位数 / p99 / 最大值）。p99 对上代码
   里的阈值常量，说明这个数是照数据定的。
3. **实验 / flag 查证。** 找到曝露表，按 flag key 拉各变体的曝露量，对照改动日期。
4. **迁移、回填、性能重写的证据。** 查查询历史，按表名或符号 + 紧的时间窗，按总耗时或读取字节
   排序，看是哪条昂贵查询促成了改动。
5. **血缘。** 目标读写的下游模型，其自身的改动历史常带动机。把这条线索交回源码史那一源，不要
   自己去追。

## 好证据长什么样

- 某个错误分类事件的计数在防御性改动之后掉到接近零
- 曝露表里出现目标的 flag key，且在落地日期附近有「已发布」/「已结束」的判定
- 一个属性的 p99 与代码里的阈值常量吻合

## 常见坑

- **仪表化 ≠ 因果。** 事件存在说明有人在意到来记它，不说明目标代码因它而存在。要与 commit / PR
  的引用配对再主张因果。
- **仪表化本身变了。** 事件量的阶跃可能是新加了一个埋点，不是用户行为变了。先看同窗口里有没有
  埋点改动。
- **schema 漂移。** 属性会演变。今天加工层里有的列，写目标代码时可能还不存在。
- **加工层刷新延迟。** 中间层按计划重建。最近几小时的数据要回原始表并按 id 去重。
- **表名因公司而异。** 报一个自己没确认存在的表上的结果，是经典失败模式。先 `SHOW TABLES`。
- **留存断崖。** 相关窗口早于表的留存期或加工层的创建日期时，这是**缺口**，不是空结果。要明说，
  免得综合者把「没结果」读成「没活动」。

## 要返回什么

每个相关发现：

- 类型（产品事件 / 实验曝露 / 用量事件 / 系统表行 / 加工层模型）
- 全限定表名与跑过的确切查询
- 查询的时间窗
- 紧凑的数字摘要（计数、分位、首末时间戳）。**不要 dump 原始行。**
- 与目标上线日期的时序关系（例如「首行 2024-08-15，PR #49074 于 2024-08-14 合入」）
- 相关性与强度：直接 / 旁证 / 弱
