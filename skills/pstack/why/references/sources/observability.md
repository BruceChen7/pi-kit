# 基础设施可观测

本机没有这个源时（`~/.agents/skills/` 下没有 `metric-analysis`、`log-analysis`、
`service-change-timeline` 这几个，或凭据没配）：**不要报「查无此项」**，在 `Sources Consulted` 里
写成 `not available in this environment`，并说清缺什么。

## 这个源里有什么

运行时的记录：线上**实际**发生了什么，而不是计划了什么或讨论过什么。

- **指标。** 团队自己埋的 counter、gauge、histogram。一个指标**存在**本身就是证据：有人觉得这个
  数值得看。
- **监控与告警。** 团队认为值得叫醒人的条件。一个 `rate_limit_hit > 10/min` 的告警，是团队担心
  这个阈值的直接证据。
- **看板。** 团队认为某个子系统重要的整理视图。
- **链路与 span。** 请求级运行时数据，回答「这里为什么慢」「这里为什么有超时」。
- **日志。** 高体量事件记录，常留着那些促使防御性代码出现的错误条件。
- **事故记录。** 带时间线与复盘链接的正式记录。
- **变更事件。** 部署、配置中心、A/B、DDL 等变更的时间线，用于对照「代码什么时候变的」。

## 怎么搜

**按探测结果选工具。** 本机可能有的工作类 skill：`metric-analysis`（指标）、`log-analysis`（日志）、
`service-change-timeline`（变更事件）。它们都在 `~/.agents/skills/` 下，各自带可执行的
`fetch-*.sh`，**调查者（子会话）有 `bash`，可以自己跑**。

调用方式读那个 skill 自己的 `SKILL.md` 与 `assets/api-reference.md`，不要凭名字猜参数。
凭据走它们自己的 `setup-config.sh` / `setup-token.sh`；没有凭据就记成缺口，不要绕。

起手顺序，从粗到细：

1. **先看变更时间线。** 目标代码的改动时间点附近有没有部署、配置或 A/B 变更。这能给出因果候选项，
   也常直接暴露动机（「这次改动紧跟在一个配置回滚之后」）。
2. **再看看板与告警。** 覆盖目标的看板/告警，记下它的查询与被盯的阈值。阈值常常就是
   「为什么这里卡在 N」的答案。
3. **然后是目标附近的指标。** 把指标轨迹与目标的上线日期对照：上线前有没有尖峰、之后有没有平稳。
   这是很强的旁证。
4. **日志要窄查，不要 dump。** 用符号、错误字符串、功能名做检索词，**务必带时间窗**
   （一般在改动前后各 30 天）。宽时间窗 + 高基数查询会跑很久。
5. **链路用于超时、重试、慢路径、跨服务行为。**

## 好证据长什么样

- 一个告警的查询与阈值，正好对上代码强制的约束（代码卡在 100，告警在请求超 100/min 时响）
- 目标作者建的看板，挂件对上代码在测或防的东西
- 一个指标在代码合入前立刻尖峰，之后平稳
- 一条变更事件的时间戳紧贴目标改动
- 事故记录引用了目标代码、同样的符号或同样的错误字符串
- 日志里出现了防御性代码要防的那种错误模式，时间在改动之前

## 常见坑

- **相关不等于因果。** 上线前有尖峰、之后平稳只是提示性的。同一窗口里可能有别的改动上线。查一下
  邻近的 PR。
- **只盯着找到的那张图。** 图反映的是做图人的取景。一张叫「重试成功率」的图，说明团队在意重试
  成功率，不说明某一行代码为它而存在。
- **仪表化 ≠ 因果。** 有指标说明有人在意到来测它，不说明代码是因为它才加的。要与 commit / PR
  日期交叉核对。
- **遥测会消失。** 指标会被改名、删除，留存期也短。找不到相关窗口的数据是**缺口**，不是空结果。
- **凭据没配。** 脚本报鉴权失败就停下记缺口，不要编发现。

## 要返回什么

每个相关条目：

- 类型（看板 / 告警 / 指标 / 日志模式 / 链路 / 变更事件 / 事故）
- 名称或标题
- 标识（ID、指标名、时间戳）
- 负责人与创建/修改日期
- 与问题相关的那个条件、查询或原文（尽量逐字）
- 相关性：它对目标代码暗示什么，连接有多强
