# 工单（Jira）

本机没有这个源时（拿不到 Jira，或 `confluence_page` 返回的 jiraKeys 为空且无别的入口）：
**不要报「查无此项」**，在 `Sources Consulted` 里写成 `not available in this environment`，
并说清缺什么。

## 这个源里有什么

- 描述功能、bug 及其动机的 issue
- 挂在 issue 上的项目文档（常是 PRD 或 spec）
- 父子 issue 关系（更大的计划 → 具体工单）
- issue 评论（澄清、范围变更、「我们为什么做这个」的动因）
- 标签（`compliance`、`customer-request`、`perf` 之类）提示动机类型
- 说明范围变化的进度更新
- 附件与关联的 PR

工单常是产品和业务上下文所在：「我们做这个是因为客户 X 提了」，或者「这是 Q3 合规计划的一部分」。

## 怎么搜

**先看锚点里的工单号。** 种子 commit 或 PR 引用了工单号（`ENG-1234`、`[BUG-567]` 形态）时，
先把那些取出来读全，包括评论。

按关键词捞相关工单：

- 功能名、关键符号、业务术语
- 多试几种说法，同一个东西在不同时期叫法不同

顺着 issue 树走：落到子 issue 时，取它的父级。子 issue 是执行层，父级常带「为什么」。

读项目文档：issue 属于某个 project 时，看挂在它上面的文档。规格与动因最常出现在项目级文档里。

看标签与里程碑。标签提示动机类别（customer-request、incident-followup、compliance），
里程碑把工作绑到截止日期上，常能反推出动机。

## 好证据长什么样

- issue 描述里有「为什么现在做」的明确说法
- 一条评论记录了范围变更的原因（「先不做 X，因为……」，或反过来）
- 标签显示外部动因（`customer-request`、`compliance`）
- 父级 issue 或它的项目文档写明这次工作的业务目标
- issue 关联到具体 PR，时间线对得上

## 常见坑

- **标题不是内容。** 关键证据常在评论或子任务里，读全。
- **只看执行层。** 停在子 issue 上会拿到「做什么」，拿不到「为什么」。往上找父级。
- **状态字段骗人。** 「完成」不代表当初的理由成立。
- **多个工单讲一件事。** 同一段代码可能被多个工单碰过。搜全，别只看第一个。
- **只有关键词命中。** 命中的是同领域的别的 issue。读全文再判。

## 要返回什么

每个相关条目：

- 工单 ID、标题、状态
- 作者与日期（创建、最后更新）
- 与问题相关的原文（尽量逐字）及其位置
- 关联的 PR 或文档
- 相关性：它对目标代码暗示什么，连接有多强
