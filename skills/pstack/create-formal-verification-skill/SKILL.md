# Create a formal verification skill

测试检查的是有人想到要写的那些用例。形式化验证检查一段声明范围内的所有用例：一个模型里所有可能的步骤顺序、一个有界范围内的所有输入，或者全部输入。这个 skill 找出仓库里这件事最要紧的地方，验证它的一个属性，并留下项目级 skill，让下一个 agent 能拿改动对着这个属性复查。

写出来的产物是给下一个 agent 的：它会冷读它、正在改代码、从没见过你这次的活。用户要能不看验证语言就看懂结论并据此行动。

默认用中文交付。属性名、命令、类型名、状态名原样保留。

## 从代码里选目标

答案从代码里取，只问观察不到的部分。用户点名了某块代码或某个 bug，就从那里起。

好目标是代码做出的一条承诺：破掉它用户会受损，而测试很少走到破它的那个用例。选仓库里最强的那条，不是最好验的那条。

## 让问题挑工具

按「回答这个问题最省」来选：模型检查器、定理证明器、SMT 验证器，或者别的。事件能不能以坏顺序发生，通常适合拿设计的小模型去模型检查，这一路在任何语言里默认是 TLA+。代码本身对每个输入都要成立，比如内存安全、溢出、数据结构不变量，通常适合跑在代码上的验证器。这门语言没有能跑在代码上的验证器，就明说，然后拿生成的输入去测真代码，不要手写一个函数模型。要求在任意规模下都成立、有界不够的属性，才可能需要证明。

优先选仓库开发者能装上并跑起来的工具，并告诉用户你为什么选它。

## 什么算好

- **忠于代码。** 模型或证明的每一处都指向 reviewer 能打开的真实代码。验证当成一步走完的，在代码里就是一步走完的。名字用这个仓库的。
- **能失败。** 从没见过失败的检查什么都不证明。每条属性都要在一份故意弄坏的代码变体上失败一次，比如摘掉一个检查、调换一步顺序。
- **发现就是发现。** 当前代码破了属性，就用代码的话报出反例。不许把属性或模型削弱到能过，也不许改产品代码，除非用户要求。
- **范围说实话。** 说清验了什么、在哪个界和哪些假设下、什么没覆盖。过了也只是模型或界内过了，不是整个系统过了。
- **不看工具也能读。** 属性和危害各用一句平话讲。反例讲成一段短步骤序列，用代码自己的词。
- **便宜到能重跑。** 一条命令、可复现的工具版本、跑得够快，快到下一个 agent 愿意在每次相关改动上跑它。
- **跟代码同步。** 记下每条检查覆盖哪些文件与函数，以及你最后一次确认「验证描述的确实是这份代码」的那个 commit。那个 commit 之后被覆盖的代码变过，下一个 agent 就能看出来这份验证要再看一眼。

## 生成 verify skill

写 `.pi/skills/verify-<area>-formal/SKILL.md`。frontmatter 用 `name: verify-<area>-formal` 加一个 description，写明这块是哪个区域、什么时候该用；没有 frontmatter 就不会注册。不要写 `disable-model-invocation: true`：它会让生成物从 system prompt 消失，agent 只能手敲 `/skill:`，而形式化验证正是给 agent 自己在改动上跑的。

光看这份 skill，下一个 agent 就要能判断改动有没有碰到被验证的代码、怎么跑这条检查、哪些是真 bug 哪些是模型写错、验证该在什么时候更新。覆盖表与 sync commit 写进 skill 里，并要求下一个 agent 只有在确认「验证确实描述了新 commit 的代码」之后才把 sync commit 往前挪。命令、路径、名词都用这个仓库真实的，不留占位符。

检查是 TLA+ 模型时，要求下一个 agent 把检查器的每条结果都讲成代码里的最短路径，而不是贴原始输出：

- 违反不变量时，按状态序列写出「哪一步把系统带到坏状态」，用代码里的动作名，不用 TLA+ 的动作名。
- 讲不清或路径超过七八步时，画一张 Mermaid 状态图或时序图，先用 `validate_mermaid` 校验、再用 `render_mermaid` 看一眼，确认图上每条边都对得上模型里的动作，然后再贴进报告。
- 检查通过时，同一份 Mermaid 图正好说明系统怎么在状态间移动，也算交付物的一部分。

图和命令都写在生成物自己的正文里，不要写成「等哪天有画图工具再说」。

生成或改完，告诉用户跑 `/reload` 或重开会话：skill 只在 pi 启动时进 system prompt，当前会话里新建的文件 agent 看不到。

## 交付前先证明它

按生成出来的 skill 自己走一遍，就像下一个 agent 那样：在真实代码上做一处故意破坏属性的 scratch 改动。它必须抓到这次破坏。然后撤掉 scratch 改动，确认检查回到开始的地方：通过，或者只剩你打算报的那几条发现。

没跑过的 verify skill 是草稿，不是交付物。skill 没抓到破坏、或者哪一步跑不起来，就修 skill 或修验证，不要改 scratch 改动。

## 交接

告诉用户：验了什么、用了哪个工具和为什么、界在哪、检查在平话里发现了什么、怎么跑、什么没覆盖。只有确实找到相邻的第二个目标时才提。

代码改了但没复查时，指向 `/skill:maintain-formal-verification-skill`。

行为侧（启动应用、按用户路径走一遍）不是这份 skill 的事，那种需求走 `/skill:create-verification-skill`。
