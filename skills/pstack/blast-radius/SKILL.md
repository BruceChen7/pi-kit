# Blast radius

在改动上线前找出它在别处会弄坏什么。用于「blast radius of X」「what could this break」「这个改动会弄坏什么」，或 review 一个你不放心的小 diff。

同类问题分工：`research` 查事实，`diagnosing-bugs` 查根因，blast radius 查别处会坏什么。

默认用中文交付，用户换语言就跟着换。`file:line`、术语、命令原样保留。

列出调用方不是这份工作。agent 一两秒就能 grep 出来。这份工作要找的是 grep 看不出来的破坏。

## 不要相信自己的说明

一份读起来对的 blast-radius 说明没有价值。它对不对都读起来很有说服力。所以不要只交说明。找出整件事依赖的那一两个事实，然后跑代码证明它。

### 你有多确定

对每个「安全所依赖」的事实，尽量往下走，走到哪一步就停在哪一步，并写清楚。

1. 你说了。单凭这一条没有价值。
2. 你指到了行。真实的 `file:line`，或者库自己的源码。
3. 你证明了坏情况到不了。把失败路径一步步走完，它走不到。
4. 你跑了。一个脚本或测试，调用真实代码，你错了它就大声失败。
5. 你在真实运行的应用里复现了。

第 4 步通常就是一个小脚本：import 应用实际发的那个库，调用你担心的那个函数。

## 步骤

1. 读改动。看 diff、它新增/修改/删除的符号、它现在行为有什么不同，包括 diff 没写出来的部分。读 PR/MR 描述与提交：`gh pr view` 或 `glab mr view`，按 `git remote -v` 选。
2. 找出「它安全所依赖的那一个事实」。大多数看起来危险的改动，只因为一个事实才安全，例如「这个调用只丢掉已经死掉的缓存项，别的什么都不做」。找到它。它成立，大部分风险一次性清掉。时间花在这里，不要花在一长串「可能」上。
3. 看 grep 停下来的地方。读你调用的那个库的源码，确认 pin 的版本与本地补丁。想清楚东西什么时候运行：microtask、卸载与 teardown、Solid 还是 React。跟着符号搜索会漏掉的东西走：API 返回的 JSON、数据库列、wire format、另一种语言读同一份字节、feature flag、三跳之后的下游代码。
4. 对每个风险诚实。给它真实的概率和真实代价。确认的风险留下，查过且排掉的单独列。同一套取证规则：只写真实 `file:line`，搜不到也是答案，绝不编造调用方或 API。
5. 证明那一个事实。写脚本或测试，调用真实代码，跑，然后把跑出来的东西贴上来。

## 交付什么

- **它做了什么。** 改了什么，包括不明显的那部分。
- **它安全所依赖的那一个事实。** 写出来，说明取证走到第几步，把证明贴上。证明不了就写 unproven。
- **风险。** 每条写清怎么坏、`file:line`、多大概率、多严重、怎么查。要紧的附上证明。
- **已排除。** 查过什么、为什么没问题。
- **合并之前。** 最便宜、能抓到真实 bug 的测试或复现，包括你写的那个脚本。

写的时候过一遍 `/skill:unslop`，引用真实代码，公开前删掉私有信息。

**Reply:** 上面这份交付，其中一个安全事实要么被证明，要么标记为 unproven。
