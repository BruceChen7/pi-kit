# Maintain a formal verification skill

形式化验证证明的是它所描述的那份东西的属性。代码变了而验证没跟，检查可以一直绿着，同时在描述一份已经不存在的代码。那种绿是最危险的，因为它看起来像一份证明。

这个 skill 是 `/skill:create-formal-verification-skill` 产出的 verify skill 的维护环，也适用于任何拿模型检查器、证明器或代码级验证器去验指定代码的项目级 skill。那类 skill 自己管「agent 在用它的过程中改代码」这一种情形；这个 skill 管那些绕开它的改动：合并、直接改的文件、以及许多 commit 累积起来的漂移。

默认用中文交付。结论名（`in sync` / `updated` / `bug` / `blocked`）与命令原样保留。

## 结论

每条检查给一个结论，并说明是哪个：

- **in sync**：从上次 sync 到现在，没有任何改动改变这条检查描述的东西，且检查通过。
- **updated**：代码变了，验证现在描述的是新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码破了属性。这是关于代码的发现，不是漂移。
- **blocked**：这条检查拉不回一致，或者跑不起来。写清到底被什么挡住。

一条检查可以同时是 `updated` 和 `bug`：更新让验证重新描述代码，然后属性在它上面失败。

## 编辑范围

只改验证本身：模型、harness、属性文件、以及 verify skill 自己。运行期间不改产品代码，除非用户要求。属性在当前代码上失败时，不许削弱属性或模型让它过，报出来。

## 过程

1. **找出这些检查。** verify skill 没有固定名字，按它做什么找：一个项目级 skill，拿模型检查器、证明器或别的验证器去验指定的代码。找到的每个都读一遍，或者只读用户点名的那一个。每条检查收集五样：属性、它覆盖的代码、界与假设、跑它的命令、以及最后一次确认它描述对了代码的那个 commit。没有 verify skill 就停下，指向 `/skill:create-formal-verification-skill`。skill 没记 sync commit，就用最后一次改动验证文件的 commit，并在报告里说清你这么做了。

2. **原样先跑一次。** 动任何东西之前，每条检查跑一次并记下结果。这一步的通过不说明代码是对的，只说明旧描述还成立。这一步的失败可能是漂移，也可能是 bug，先别判定，等到第 5 步。

3. **读被覆盖代码的每一处改动。** 把覆盖的文件从 sync commit diff 到当前 commit，逐条读 commit message。也要找挪走的代码：被覆盖的函数改名、拆开、搬到别的文件，仍然算被覆盖。还要找碰到被守护状态的新代码，比如一个新函数在写同一批字段。每处改动归入以下之一：

   - **没有影响。** 改动没改变验证描述的任何东西，比如格式、注释、验证没覆盖的代码路径。对着模型或 harness 核，不要对着 commit message 核。
   - **验证不再描述这份代码。** 原本一步走完的动作现在两步了、分支增删了、检查挪位置了、有新路径能到被守护的状态了、取值范围变了。模型或 harness 必须改。
   - **承诺是故意变的。** 改动改变了代码承诺的东西，而且改动里有证据说这是有意的：文档注释、测试、changelog、commit message。属性必须改，并且你要引用那份证据。
   - **承诺可能被破了。** 代码变了，没有任何证据说承诺变过。后面跟着的失败按 bug 候选处理。

4. **从代码改，不从结果改。** 改模型或 harness，让每个变过的部分重新指向 reviewer 能打开的真实代码，代码里一步走完的动作在验证里也只算一步。先按代码写完更新，再重跑，不要看着「怎么才能变绿」去写。只有承诺确实故意变了才改属性，并写下旧措辞、新措辞和证据。界保持不变，除非改动让它变错了；确实要缩界就在报告里写出来。

5. **重跑并逐条判定。**

   - **通过：** 这一次的过，可能只是因为这份描述已经失去了失败的能力。按属性守护的方式弄坏新代码，比如摘掉一个新加的检查、调换一步新加的顺序，确认检查抓得到，然后撤掉。
   - **失败：** 拿反例对着真代码一步一步复盘。某一步在代码里根本不可能发生，就是验证写错了，修验证并说清错在哪。每一步都可能发生，就是 bug：点出引入它的 commit，用代码自己的话把反例讲成一段步骤序列，用一句话说清危害。如果一条便宜的测试或复现能对着真代码证明这个 bug，把它作为证据放进报告，但不提交进产品代码。

6. **更新 verify skill。** 更新每条检查覆盖的代码、命令、界、假设和 sync commit。sync commit 设成你检查过的那个 commit。结论是 `blocked` 的检查不许动 sync commit，并在报告里说明。然后按下一个 agent 的方式把 verify skill 走一遍，确认它的步骤还能跑。

## 报告

逐条检查告诉用户：

- 结论，以及你读过的 commit；
- 验证改了什么、为什么，每条一句理由：代码变形状了，或者承诺故意变了（带证据）；
- 重跑结果，以及你用来证明「更新后的检查仍然能失败」的那次破坏；
- 每个 bug 用平话讲：反例讲成代码里的步骤、危害、引入它的 commit；
- 验证仍然没覆盖什么，包括那些它该覆盖却没覆盖的新代码。

明说哪条失败是验证漂移、哪条是代码 bug。一条检查在你更新前是绿的、更新后红了，就说清旧的绿是建立在过期描述上的。

验证的更新单独开一份改动，不要和产品修复混在一起。要开 PR 时按 `git remote -v` 选 `gh` 或 `glab`。

行为侧的维护（launch / drive / feature map 过期）不是这份 skill 的事，走 `/skill:maintain-verification-skill`。
