# Correct

同一个纠正出现第二次，就不要再靠下次提醒。改仓库，让下一个 agent 犯不了这个错。

前提：每个贡献者都是一个只看得到自己打开过的文件、会抄最近一个例子、会走「能编译的最短路径」的 agent。把仓库设计成「从一个文件看是对的改动，对整个仓库也对」。

默认用中文交付。

## 一、找出错误类别

先读最近的 commit、revert、review comment（`gh pr view --comments` 或 `glab mr view`，按 `git remote -v` 选）、`AGENTS.md`、以及解释 workaround 的注释。

把错误分类。同一类出现两次才算数。一次是意外，两次是设计问题。

## 二、按能生效的最高层级修

从高到低，能停在哪一层就停在哪一层：

1. **用架构消掉它。** 每份状态只有一个 owner，每件事只有一种被支持的做法。把内部藏起来，让错误 import 直接失败。手工同步的列表换成单一真源。删掉旧做法和 agent 会抄的死代码。
2. **用类型挡住它。** 让坏状态写不出来。如果坏代码还能编译，加一条 lint 或 CI 检查，报错信息里直接写该用哪个文件、哪个类型、哪个函数。模式已经普遍存在时，只在新改动增加数量时失败。
3. **用测试兜住它。** 修掉或删掉那种「行为坏了还绿」或「只改内部就红」的测试。
4. **最后才写文档或规则。** 只写判断类的东西。agent 跳过文档时不会有任何东西失败，所以它排在最后。

## 三、现在就修，并证明

挑出现频率最高的几类，现在就修，一个 commit 一类。每条新检查都要证明它能在真实的历史错误上失败。本地和 CI 跑同一条命令。

例外要写在出问题的那一行，带上原因、失效日期和人工批准。

## 四、维护规则表

在仓库根目录的 `AGENTS.md` 里维护一张表，左边是规则，右边是什么东西在强制它。文件不存在就新建一个，只写这次要强制的规则。

用户每次纠正，就修错并把规则加进表里：

- 规则已经在了，但没有任何东西强制它，这是重复犯错，本次改动里按最高层级修掉。
- 规则对应的错已经不可能发生，就把规则删掉。

`AGENTS.md` 是 pi 每次会话自动加载的 context file（工作目录与父目录都会被扫描）。`.pi/lessons.md` 只是人读的经验记录，不会自动加载，不能当强制层。

**Reply:** 每个错误类别配上证据、选了哪一层、以及为什么更高一层不成立。
